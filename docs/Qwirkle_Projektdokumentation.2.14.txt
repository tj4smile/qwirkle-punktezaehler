1. ÜBERBLICK
================================================================================

Die App ersetzt Stift und Zettel beim Brettspiel "Qwirkle". Sie erfasst pro
Runde die Punkte aller Spieler, berechnet die Qwirkle-Boni und den
Endspielbonus automatisch, zeigt Spielverlauf und Endauswertung und führt eine
Langzeitstatistik über alle gespielten Partien.

Funktionsumfang:

  - Spielerverwaltung (anlegen, umbenennen, Farbe ändern, löschen)
  - Neues Spiel mit 2 bis 7 Spielern, optional als Testspiel
  - Punkteerfassung pro Runde (alle Spieler untereinander)
  - Automatische Bonusberechnung (6 Punkte pro Qwirkle)
  - Spielverlauf als Tabelle mit Summenzeile
  - Spielende mit Endspielbonus (6 Punkte)
  - Endauswertung mit Platzierungen und Qwirkle-Balkendiagramm
  - Laufendes Spiel bleibt gespeichert und kann fortgesetzt werden
  - Langzeitstatistik mit Kennzahlen, Spielerstatistik, Spieleliste und Rekorden
  - Hell- und Dunkelmodus: bei dunklem System immer dunkel, bei hellem System
    per Schalter auf der Startseite wählbar
  - Zweisprachig: Deutsch bei deutscher Systemsprache, sonst Englisch
  - Daten sichern, wiederherstellen und exportieren (JSON-Sicherung, CSV für
    Excel)
  - Autorenhinweis auf der Startseite
  - Vollständig offline, alle Daten liegen lokal in einer SQLite-Datenbank

Vorlagen für die Umsetzung waren der Phasenplan (Phase 1 bis 5) und die
Wireframes 01 bis 09.

4. ARCHITEKTUR
================================================================================

Die App folgt einer einfachen, geschichteten Architektur (MVVM):

  +--------------------------------------------------------------+
  |  UI-Schicht (Jetpack Compose)                                |
  |  Screens in ui/screens, Komponenten in ui/components         |
  +------------------------------+-------------------------------+
                                 | beobachtet StateFlow, ruft Methoden auf
  +------------------------------v-------------------------------+
  |  ViewModel-Schicht (viewmodel/)                              |
  |  hält UI-Zustand, ruft Repository in viewModelScope auf      |
  +------------------------------+-------------------------------+
                                 |
  +------------------------------v-------------------------------+
  |  Repository (data/repository/GameRepository)                 |
  |  Fachlogik der Datenschicht, Validierung, Berechnung         |
  +------------------------------+-------------------------------+
                                 |
  +------------------------------v-------------------------------+
  |  DAOs (data/dao)  ->  Room-Datenbank (data/database)         |
  +--------------------------------------------------------------+

Grundprinzipien:

  - Unidirektionaler Datenfluss: UI zeigt Zustand an und meldet Ereignisse an
    das ViewModel. Datenbank-Änderungen kommen über Flows zurück.
  - Eine einzige Wahrheit: Der Spielstand liegt in der Datenbank. Gerechnet
    wird beim Anzeigen (siehe GameCalculations), nicht gespeichert.
  - Manuelle Dependency Injection: QwirkleApp erzeugt Datenbank, GameRepository,
    BackupRepository und AppSettings einmalig. Die Composables holen sie mit
    rememberRepository(), rememberBackupRepository() und rememberSettings()
    und übergeben sie an die ViewModel-Factory.

Beispiel für die Verdrahtung in einem Screen:

  @Composable
  fun PlayerManagementScreen(
      onBack: () -> Unit,
      viewModel: PlayerViewModel = viewModel(
          factory = PlayerViewModel.factory(rememberRepository())
      )
  ) { ... }

Jedes ViewModel besitzt dafür eine companion-Funktion factory(...).

6. DATENMODELL (ROOM)
================================================================================

6.1 Entity-Relationship-Übersicht
---------------------------------

  players 1 ---- n game_players n ---- 1 game_history 1 ---- n rounds
     |                                                          |
     |                                                          | 1
     |                                                          |
     |                        n                                 n
     +----------------- round_scores ---------------------------+

  - game_players verbindet Spieler mit Spielen (inkl. Reihenfolge).
  - round_scores gehört zu genau einer Runde und genau einem Spieler.
  - Löscht man ein Spiel, werden dessen Runden, Rundenpunkte und Teilnehmer
    per CASCADE mitgelöscht.
  - Spieler werden nie hart gelöscht (siehe players.isActive).

6.2 Tabelle players  (Entity Player)
------------------------------------
  id          Long, Primärschlüssel, autoGenerate
  name        String
  colorIndex  Int          Index 0 bis 6 in PlayerColors
  isActive    Boolean      true = sichtbar, false = "gelöscht" (Soft Delete)

6.3 Tabelle game_history  (Entity GameHistory)
----------------------------------------------
  id                Long, Primärschlüssel, autoGenerate
  date              Long        Startzeit in Millisekunden (Epoch)
  playerCount       Int
  totalPoints       Int         Summe ALLER Spieler inkl. Boni (erst nach
                                finishGame gefüllt, vorher 0)
  totalQwirkles     Int         Summe aller Qwirkles (erst nach finishGame)
  isTestGame        Boolean     Testspiel, wird nicht in Statistik gezählt
  isFinished        Boolean     false = läuft noch, true = gespeichert
  endBonusPlayerId  Long?       Spieler mit Endspielbonus, null = niemand

6.4 Tabelle game_players  (Entity GamePlayer)
---------------------------------------------
  id          Long, Primärschlüssel, autoGenerate
  gameId      Long   -> game_history.id  (ON DELETE CASCADE, Index)
  playerId    Long   -> players.id       (Index)
  position    Int    Spielreihenfolge, beginnt bei 0

6.5 Tabelle rounds  (Entity Round)
----------------------------------
  id           Long, Primärschlüssel, autoGenerate
  gameId       Long   -> game_history.id  (ON DELETE CASCADE, Index)
  roundNumber  Int    beginnt bei 1, fortlaufend pro Spiel

6.6 Tabelle round_scores  (Entity RoundScore)
---------------------------------------------
  id        Long, Primärschlüssel, autoGenerate
  roundId   Long   -> rounds.id   (ON DELETE CASCADE, Index)
  playerId  Long   -> players.id  (Index)
  points    Int    eingegebene Punkte OHNE Qwirkle-Bonus
  qwirkles  Int    Anzahl Qwirkles in dieser Runde (0 bis 3 in der Oberfläche)

WICHTIG: Der Qwirkle-Bonus wird NICHT gespeichert, sondern bei Bedarf über
GameRules berechnet. Dadurch gibt es genau eine Stelle, an der die Regel steht.

6.7 Relationen (Datenklassen in data/model)
-------------------------------------------
  RoundWithScores   @Embedded Round + @Relation List<RoundScore>
  GameWithRounds    @Embedded GameHistory + @Relation List<RoundWithScores>
  StatisticsSummary Ergebnisklasse der Statistik-Abfrage
  ScoreEntry        (playerId, points, qwirkles) - Eingabe aus der UI

6.8 Datenbank
-------------
  AppDatabase  DATABASE_VERSION = 1, exportSchema = true, Dateiname "qwirkle.db"
  Entities     Player, GameHistory, GamePlayer, Round, RoundScore
  Migrationen  .addMigrations(*Migrations.ALL)  (siehe Abschnitt 20)
  Zugriff      AppDatabase.getInstance(context)  (thread-sicherer Singleton)

7. FACHREGELN UND BERECHNUNGEN
================================================================================

7.1 Konstanten (util/GameRules)
-------------------------------
  QWIRKLE_BONUS = 6      Punkte pro Qwirkle
  END_BONUS     = 6      Endspielbonus
  MIN_PLAYERS   = 2
  MAX_PLAYERS   = 7

7.2 Rundenpunkte
----------------
  roundTotal(points, qwirkles) = points + qwirkles * 6

Beispiel: Anna gibt 18 Punkte ein und hat 2 Qwirkles.
  Bonus       = 2 * 6 = 12
  Rundenwert  = 18 + 12 = 30

7.3 Gesamtpunkte eines Spielers (GameCalculations.playerTotals)
---------------------------------------------------------------
  Summe aller roundTotal-Werte des Spielers
  + 6 (END_BONUS), falls er der Spieler mit dem Endspielbonus ist

7.4 Platzierungen (GameCalculations.ranking)
--------------------------------------------
Absteigend nach Gesamtpunkten. Gleiche Punktzahl ergibt gleichen Rang
(Beispiel: 1., 2., 2., 4.).

7.5 Spielergebnis (GameRepository.finishGame)
---------------------------------------------
  totalPoints   = Summe aller roundTotal-Werte aller Spieler + Endspielbonus
  totalQwirkles = Summe aller Qwirkles aller Spieler
  isFinished    = true

Hinweis: Die "Gesamtpunkte" eines Spiels sind die Summe ALLER Spieler (so
sehen es auch die Wireframes für "Letztes Spiel" und "Langzeitstatistik" vor).
Rekorde in der Statistik beziehen sich daher auf diese Spielsumme, nicht auf
die Einzelleistung eines Spielers.

7.6 Eingaberegeln der Punkteerfassung
-------------------------------------
  - Punktefeld: nur Ziffern, maximal 2 Stellen (0 bis 99; ältere Werte mit
    3 Stellen bleiben les- und bearbeitbar)
  - Alle Punktefelder sind mit 0 vorbelegt; "Runde speichern" ist daher
    immer möglich (bis zum Laden im Bearbeiten-Modus gesperrt)
  - Qwirkles: Zähler von 0 bis 3 pro Runde (Konstante MAX_QWIRKLES = 3)
  - "Beenden" ist erst möglich, wenn mindestens eine Runde gespeichert ist

7.7 Spielernamen
----------------
  - Leer oder nur Leerzeichen: nicht erlaubt (EMPTY)
  - Maximal 20 Zeichen (TOO_LONG)
  - Eindeutig unter den AKTIVEN Spielern, Groß-/Kleinschreibung egal
    (DUPLICATE). Ein "gelöschter" Spieler blockiert seinen Namen nicht.
  - Namen werden vor dem Speichern getrimmt.

7.8 Farbvergabe
---------------
  7 feste Farben (Rot, Blau, Grün, Gelb, Lila, Orange, Türkis). Ein neuer
  Spieler bekommt automatisch die erste Farbe, die kein aktiver Spieler hat.
  Sind alle vergeben, wird reihum weitergezählt. Die Farbe ist beim Bearbeiten
  änderbar. Mehrere Spieler dürfen dieselbe Farbe haben.

7.9 Soft Delete von Spielern
----------------------------
"Spieler löschen" setzt isActive = false. So bleiben alte Spiele und die
Statistik vollständig, und ein Spiel zeigt auch später noch die richtigen
Namen. Gelöschte Spieler erscheinen nicht mehr in der Spielerverwaltung und
nicht in der Auswahl für neue Spiele, wohl aber in bereits angelegten Spielen
(GamePlayerDao fragt ohne isActive-Filter ab).

  discardGame(gameId)                          löscht Spiel samt Abhängigen
  cleanUpUnfinishedGames()

Historie und Statistik:
  getFinishedGames(), getLastFinishedGame(), gameCount(), getStatistics(),
  getPlayerStatistics(), deleteGame(gameId)

9.1 Routen (navigation/NavRoutes)

  RESULTS     "results/{gameId}"    Endauswertung

Hilfsfunktionen: setup(ids, isTest), scoring(id), history(id), gameEnd(id),
results(id). Das Argument gameId ist vom Typ Long (NavType.LongType);
playerIds ist ein String "1,2,3" (Spielreihenfolge), testGame ein Boolean.

9.2 Navigationsgraph
--------------------

  HOME
   |-- Spieler verwalten ----------------> PLAYERS
   |-- Statistik ------------------------> STATISTICS
   |-- Daten sichern & wiederherstellen --> DATA
   |-- Info & Spielregeln ---------------> INFO
   |-- Erinnerungskarte "Jetzt sichern" --> DATA
   |-- Spiel fortsetzen (laufendes Spiel)-> HISTORY(id)
   '-- Neues Spiel ----------------------> NEWGAME
                                             |  Weiter
                                             v
                                         SETUP (Reihenfolge & Farben)
                                             |  Los geht's (Spiel wird angelegt)
                                             v
                                         SCORING(id)  <------------+
                                             |  Runde speichern    |
                                             v                     | Runde
                                         HISTORY(id) --------------+ hinzufügen
                                             |  Beenden
                                             v
                                         GAMEEND(id)
                                             |  Endauswertung anzeigen
                                             v
                                         RESULTS(id)
                                             |  Speichern / Verwerfen
                                             v
                                           HOME

  Zusätzlich: SCORING hat ebenfalls "Beenden" -> GAMEEND (ab Runde 2).
  HISTORY -> EDITROUND(gameId, roundId) durch Antippen einer Rundenzeile;
  nach "Änderung speichern" oder Zurück geht es per popBackStack zurück zu
  HISTORY.
  NEWGAME hat bei leerer Spielerliste einen Knopf -> PLAYERS.

9.3 Rückstapel (Back Stack)
---------------------------
  - NEWGAME -> SETUP -> SCORING: beim Start wird NEWGAME (samt SETUP) per
    popUpTo entfernt.
  - SCORING -> HISTORY und HISTORY -> SCORING: der jeweils verlassene
    Bildschirm wird per popUpTo entfernt. Der Stapel bleibt dadurch flach
    (HOME -> aktueller Spielbildschirm).
  - GAMEEND und RESULTS werden normal gestapelt. Die Zurück-Taste führt von
    RESULTS zu GAMEEND (Endbonus kann geändert werden) und von GAMEEND zum
    letzten Spielbildschirm.
  - In SCORING und HISTORY führt "←" und die Systemtaste zum Startbildschirm
    (goHome = popBackStack(HOME)). Das Spiel bleibt gespeichert.
  - RESULTS -> HOME nach Speichern oder Verwerfen (goHome).

10.10 Spielerstatistik (util/PlayerStatistics)
----------------------------------------------
  Reine Rechenfunktion compute(players, games, participants) -> List<PlayerStats>.
  Das Repository (GameRepository.getPlayerStatistics) kombiniert dafür drei
  Datenströme: alle Spieler (auch inaktive), alle gespeicherten Nicht-
  Testspiele mit Runden (GameHistoryDao.getFinishedGamesWithRounds) und deren
  Teilnehmer (GamePlayerDao.getParticipantsOfFinishedGames). Es ändert sich
  nichts am Datenbankschema (keine Migration nötig).
  Regeln:
    - Punkte einer Partie = Rundenpunkte inkl. Qwirkle-Boni + Endspielbonus.
    - Sieg = Platz 1. Bei Punktgleichstand an der Spitze zählt der Sieg für
      alle Beteiligten.
    - Inaktive Spieler nehmen am Ranking alter Partien teil, erscheinen aber
      nicht in der Ausgabe.
    - Partien ohne Runden werden übersprungen.
    - Sortierung: Siege, Siegquote, Ø Punkte (absteigend), dann Name.
  PlayerStats: player, games, wins, totalPoints, bestPoints, totalQwirkles;
  abgeleitet: winRate, averagePoints, averageQwirkles.

10.12 Sicherungs-Erinnerung (util/BackupReminder)
-------------------------------------------------

================================================================================
12. SPIELABLAUF (ENDE-ZU-ENDE)
================================================================================

  1. Spieler anlegen (PlayerManagementScreen).
  2. Neues Spiel: 2 bis 7 Spieler auswählen, optional Testspiel, starten.
     -> game_history (isFinished = false) + game_players werden angelegt.
     -> Ein eventuell vorhandenes altes, unfertiges Spiel wird gelöscht.
  3. Punkteerfassung: für alle Spieler Punkte und Qwirkles eintragen,
     "Runde speichern". -> rounds + round_scores (atomar).
  4. Spielverlauf: Tabelle prüfen, weitere Runden hinzufügen (Schritt 3 und 4
     wechseln sich ab), einzelne Runden antippen und Punkte/Qwirkles ändern
     oder die letzte Runde löschen.
  5. Beenden: Spielende-Bildschirm, Endspielbonus-Spieler wählen.
     -> game_history.endBonusPlayerId wird gesetzt.
  6. Endauswertung: Platzierungen und Diagramm ansehen. Die Summen werden
     live berechnet.
  7. "Spiel speichern": finishGame schreibt totalPoints, totalQwirkles und
     isFinished = true. Nicht-Testspiele erscheinen ab jetzt in Letztes Spiel,
     Spieleliste und Statistik.
     Alternativ "Spiel verwerfen": das Spiel wird komplett gelöscht.

Unterbrechung: Verlässt man ein laufendes Spiel (Zurück, App schließen), bleibt
es mit isFinished = false in der Datenbank. Die Startseite bietet "Spiel
fortsetzen" an, das zum Spielverlauf führt.

13. DESIGN UND THEME
================================================================================

  - Material 3 mit festen Markenfarben, keine dynamischen Farben.
  - QwirkleTheme(darkTheme) in ui/theme/Theme.kt. MainActivity bestimmt:
        darkTheme = isSystemInDarkTheme() || AppSettings.darkModePreferred
    Systemdesign dunkel -> immer dunkel. Systemdesign hell -> Wahl des Nutzers
    (Schalter auf der Startseite, Standard: hell).
  - Edge-to-Edge: enableEdgeToEdge() in MainActivity; ein SideEffect im Theme
    setzt die Helligkeit der Symbole in Status- und Navigationsleiste passend
    zum Design (dunkle Symbole auf hellem Grund und umgekehrt).
  - Markenfarben: Blau (primary), Orange (secondary), Grün (tertiary), je
    eine helle Variante für den Dunkelmodus (Color.kt).
  - Spielerfarben: PlayerColors.argb(index) bzw. playerColor(index) als
    Compose-Color. Die 7 Farben sind fest (siehe Abschnitt 7.8).
  - Jeder Bildschirm nutzt Surface + Modifier.screenPadding() (ui/components/
    ScreenPadding.kt): safeDrawingPadding() plus ScreenLayout.TopExtra (12 dp)
    zusätzlich oben. Den Abstand zum oberen Rand ändert man zentral über
    ScreenLayout.TopExtra. Die Startseite hat zusätzlich eigenen Abstand oben.
  - Es werden keine Icon-Bibliotheken verwendet. Der Zurück-Pfeil (BackButton)
    wird mit Canvas gezeichnet, weil das Textzeichen "←" auf manchen Geräten
    zu klein oder gar nicht dargestellt wurde. Weitere Symbole sind
    Textzeichen (−, +, ★).
  - Lokalisierung: Alle sichtbaren Texte stehen in Ressourcen.
        res/values/strings.xml      Englisch (Standard)
        res/values-de/strings.xml   Deutsch
    Ist die Systemsprache Deutsch, erscheint die App deutsch, bei jeder
    anderen Sprache englisch. Eine eigene Sprachauswahl in der App gibt es
    nicht. Der Name "author_name" ist translatable="false".
    Datumsformat: Deutsch TT.MM.JJJJ, sonst das lokale Format
    (DateFormat.MEDIUM). Zahlen folgen der Geräte-Sprache.
  - App-Icon: adaptives Icon (Vordergrund: sechs Qwirkle-Steine in 2x3,
    Hintergrund: dunkles Blau) mit einfarbiger Variante für Themed Icons.


================================================================================
14. KONVENTIONEN
================================================================================

  Namensgebung
    - Entities: Substantiv im Singular (Player, Round, RoundScore)
    - Tabellennamen: snake_case, Plural (players, round_scores)
    - Spaltennamen: camelCase wie die Kotlin-Properties
    - Screens: <Name>Screen, ViewModels: <Name>ViewModel
    - Routen: Konstanten in NavRoutes, Aufbau mit Hilfsfunktionen

  Struktur
    - Ein Screen pro Datei, private Hilfs-Composables in derselben Datei
    - Screens bekommen Navigationsaktionen als Lambdas (onBack, onFinish, ...)
      und kennen den NavController nicht
    - Datenbankzugriff ausschließlich über das Repository, nie direkt aus der
      UI oder dem ViewModel an den DAOs vorbei
    - Mehrere zusammengehörige Schreibvorgänge laufen in einer @Transaction
      (RoundDao.saveRound, GamePlayerDao.startGame)

  Kotlin / Compose

  - Datenbank: Version 1. Migrationen sind eingerichtet, aber noch keine
    geschrieben. Jede Schemaänderung braucht Versionserhöhung, Migration und

    nur vor dem Spielstart.
  - Eine Spielunterbrechung wird erst nach der ersten gespeicherten Runde

  - Der Spielverlauf teilt die Breite gleichmäßig auf. Ab 5 Spielern zeigt
    die Kopfzeile nur Farbpunkt und zwei Buchstaben; bei gleichen
    Anfangsbuchstaben hilft der Farbpunkt.
  - Nur Hochformat getestet/ausgelegt; Querformat und Tablets sind nicht
    gesondert gestaltet.
  - Nur zwei Sprachen (Deutsch, Englisch). Keine Sprachwahl in der App.
  - Der Schalter für das dunkle Design wirkt nur bei hellem Systemdesign.
  - ViewModels und Compose-Oberflächen haben noch keine automatischen Tests
    (siehe Abschnitt 19).
  - Die Standard-Typografie des Projekts wird verwendet; Type.kt der Vorlage
    ist ungenutzt.

18. GLOSSAR
================================================================================

  Qwirkle            Eine Reihe aus sechs Steinen derselben Farbe oder Form;
                     bringt 6 Bonuspunkte.
  Endspielbonus      6 Punkte für den Spieler, der den letzten Stein legt.
  Runde              Ein Durchgang, in dem für jeden Spieler Punkte erfasst
                     werden.
  Testspiel          Spiel, das nicht in Statistik und Historie zählt.
  Laufendes Spiel    Spiel mit isFinished = false (nicht gespeichert).
  Soft Delete        "Löschen" durch Deaktivieren (isActive = false).
  DAO                Data Access Object, Room-Schnittstelle für SQL.
  Flow / StateFlow   Kotlin-Datenströme, die bei Datenänderungen neue Werte
                     liefern.
  KSP                Kotlin Symbol Processing, erzeugt den Room-Code beim
                     Build.
  DI                 Dependency Injection, hier manuell in QwirkleApp.
  Migration          Skript, das eine Datenbank von Version n auf n+1 hebt,
                     ohne Daten zu verlieren.
  Schema-Datei       JSON-Beschreibung einer Datenbankversion (app/schemas).
  SAF                Storage Access Framework: der Android-Dateidialog zum
                     Speichern und Öffnen von Dateien.
  BOM                Byte-Order-Mark am Dateianfang; sorgt dafür, dass Excel
                     eine CSV-Datei als UTF-8 liest.

20. DATENBANK-MIGRATIONEN
================================================================================

Grundlage: DATABASE_VERSION (AppDatabase.kt), exportSchema = true, das
Room-Gradle-Plugin mit schemaDirectory("$projectDir/schemas") und die Datei
data/database/Migrations.kt (object Migrations, Liste ALL, aktuell leer).

Beim ersten Build entsteht
  app/schemas/com.thomas.qwirkle.data.database.AppDatabase/1.json
Diese Datei muss im Projekt (und in der Versionsverwaltung) bleiben.

Ablauf bei einer Schemaänderung (Beispiel: neue Spalte):
  1. Entity ändern.
  2. DATABASE_VERSION um 1 erhöhen.
  3. In Migrations.kt eine Migration(n, n+1) mit den SQL-Anweisungen schreiben
     und in ALL eintragen.
  4. Bauen: Room erzeugt die neue Schema-Datei (n+1.json). Alle Schema-Dateien
     behalten.
  5. MigrationTest um einen Test n -> n+1 erweitern
     (helper.runMigrationsAndValidate).
  6. Backup-Format prüfen: ändert sich der Aufbau der Daten, BackupJson.
     FORMAT_VERSION erhöhen und decode() so erweitern, dass alte Sicherungen
     weiterhin lesbar bleiben.

Niemals fallbackToDestructiveMigration() verwenden: bei einem Update würden
alle Spiele der Nutzer gelöscht.


================================================================================
21. EXPORT, SICHERUNG UND IMPORT
================================================================================

21.1 Ablauf
-----------
  DataScreen -> DataViewModel -> BackupRepository -> BackupDao
  Die Datei wird über den Android-Dateidialog (Storage Access Framework)
  gewählt; es sind keine zusätzlichen Berechtigungen nötig.

21.2 JSON-Sicherung (BackupJson)
--------------------------------
  Enthält alle Tabellen, auch inaktive Spieler und das laufende Spiel.
  Kopf:    format = "qwirkle-backup", formatVersion, schemaVersion,
           exportedAt (Millisekunden)
  Listen:  players, games, gamePlayers, rounds, roundScores
  endBonusPlayerId wird als null geschrieben, wenn nicht gesetzt.

  Prüfung beim Einlesen (bevor irgendetwas gelöscht wird):
    - gültiges JSON mit format = "qwirkle-backup"    sonst NOT_A_BACKUP
    - formatVersion nicht größer als bekannt          sonst NEWER_VERSION
    - alle Felder vorhanden und vom richtigen Typ     sonst NOT_A_BACKUP
    - IDs eindeutig, alle Verweise gültig, keine negativen Punkte, keine
      leeren Namen, Rundennummer >= 1                 sonst INCONSISTENT
  Dateien über 20 MB werden abgelehnt (TOO_LARGE).

21.3 Wiederherstellung (BackupDao.replaceAll)
---------------------------------------------
  Eine Transaktion: erst löschen (round_scores, rounds, game_players,
  game_history, players), dann einfügen (players, game_history,
  game_players, rounds, round_scores). Schlägt ein Schritt fehl, wird alles
  zurückgerollt und die bisherigen Daten bleiben unverändert. Die
  ursprünglichen IDs bleiben erhalten; neue Datensätze erhalten danach
  fortlaufend höhere IDs.

21.4 CSV-Export (CsvExporter)
-----------------------------
  Eine Zeile pro Spieler und Runde. Spalten:
    Datum, Spiel, Testspiel, Abgeschlossen, Runde, Spieler, Punkte, Qwirkles,
    Qwirkle-Bonus, Rundenpunkte
  (Überschriften in der App-Sprache; Datum als JJJJ-MM-TT.)
  - Rundenpunkte = Punkte + Qwirkle-Bonus.
  - Der Endbonus steht als eigene Zeile (Runde = "Endbonus", Rundenpunkte 6),
    nur bei abgeschlossenen Spielen mit gewähltem Endbonus-Spieler. Die Summe
    der Spalte Rundenpunkte je Spiel entspricht damit den Gesamtpunkten.
  - Spielerreihenfolge innerhalb einer Runde = Spielreihenfolge.
  - Trennzeichen: ";" bei deutscher Sprache, sonst ",".
  - UTF-8 mit BOM (Umlaute in Excel), Zeilenende CRLF.
  - Textfelder mit Trennzeichen oder Anführungszeichen werden maskiert;
    Namen, die mit = + - @ beginnen, erhalten ein vorangestelltes ', damit
    Excel sie nicht als Formel ausführt.
  - Enthält auch Testspiele und das laufende Spiel (Spalten Testspiel und
    Abgeschlossen dienen zum Filtern).

22. VERTEILUNG (APK, SIGNIERUNG)
================================================================================

  - Für Freunde und eigene Geräte: signierte Release-APK
    (Build -> Generate Signed App Bundle / APK -> APK). Installation durch
    Öffnen der Datei; "Installation aus unbekannten Quellen" muss für die
    öffnende App erlaubt sein.
  - AAB (App Bundle) nur für den Google Play Store.
  - Keystore-Datei und Passwörter sichern (z. B. Passwortmanager und Kopie an
    einem zweiten Ort). Ohne denselben Schlüssel lassen sich spätere Updates
    nicht über die installierte App einspielen.
  - versionCode vor jedem Update erhöhen (app/build.gradle.kts, defaultConfig),
    versionName nach Belieben.
  - Bekannter Befund: Die Release-APK lief auf Android 17 nicht, die Debug-APK
    schon. Vermutete Ursache: R8-Optimierung. Abhilfe: in der Release-
    Konfiguration die Optimierung abschalten (optimization { enable = false }).
    Eine Release-APK lässt sich nicht über eine Debug-Installation spielen
    (andere Signatur): erst deinstallieren, vorher Sicherung anlegen (Abschnitt 21).
  - Google verlangt für die Installation auf zertifizierten Geräten zunehmend
    eine Entwicklerverifizierung; für kleine Verteilung (begrenzte Anzahl
    Geräte) gibt es eine eingeschränkte Variante. Aktuelle Regeln bei Google
    nachlesen.
